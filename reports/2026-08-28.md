## Selected opportunity

**Repository:** `paperclipai/paperclip`

**Issue:** #12328 — `local-process sandbox proxy: network_target_denied reason is unreachable on the CONNECT path`

**Selected independently useful slice:** document the current, already-shipped denial contract next to the adapter utilities while the proposed CONNECT response-header code change is still pending review.

This is not presented as closing #12328. It is a useful part of the issue's own requested work: document HTTP 403 from the sandbox proxy as the stable “denied by policy” signal and explain that CONNECT callers must not rely on the response body. This prevents adapter/integration authors from treating a policy block as a flaky-network event or attempting unsafe bypass behavior.

## Evidence and repository observations

`packages/adapter-utils/src/local-process-sandbox.ts` on upstream `master` currently does the following:

- Plain HTTP denial calls `writeProxyError(..., 403, "network_target_denied", ...)`, so clients receive status 403 and a JSON error body.
- CONNECT denial calls `connectProxyError(...)`, which writes the same structured JSON body after an HTTP 403 status line.
- The existing `local-process-sandbox.test.ts` regression verifies that the CONNECT response contains HTTP 403, JSON content type, and the structured denial body on the wire.

Issue #12328 documents the protocol-level usability gap: mainstream CONNECT clients commonly retain the status but do not expose that non-2xx CONNECT body to application code. The issue proposes a future `X-Paperclip-Denied-Reason` header and separately asks for the 403 denial contract to be documented.

Paperclip's `CONTRIBUTING.md` was reviewed. It prioritizes small focused changes, duplicate searches, complete PR-template sections, accurate validation claims, Draft/CI review, and Greptile 5/5. `ROADMAP.md` was also reviewed; this documentation clarification is not a new roadmap-level core feature.

## Expected user/developer impact

This documentation reduces a concrete integration failure mode. An adapter or client that sees a sandbox-proxy 403 can classify it as a policy denial instead of retrying it as a transient transport failure. CONNECT clients are warned not to depend on a response body they may never receive. The fail-safe wording also discourages weakening sandbox policy to “fix” a denied request.

The change does not claim to solve the structured-reason accessibility problem itself. A response header remains the stronger follow-up if maintainers accept #12328's implementation direction.
