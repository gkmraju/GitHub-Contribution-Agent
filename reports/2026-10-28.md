## Selection, evidence and duplicate review

Selected [OpenCLI issue #2714](https://github.com/jackwener/OpenCLI/issues/2714), reported 2026-10-26, concerning HTTP 400 from LinkedIn job search when location or keywords contain commas, colons, parentheses, or apostrophes. The reporter supplied a reproducible example (`São Paulo, Brazil`) and a proposed encoding strategy. Inspected the current [source](https://github.com/jackwener/OpenCLI/blob/main/clis/linkedin/search.js), [existing tests](https://github.com/jackwener/OpenCLI/blob/main/clis/linkedin/search.test.js), [contribution guide](https://github.com/jackwener/OpenCLI/blob/main/CONTRIBUTING.md), [package scripts](https://github.com/jackwener/OpenCLI/blob/main/package.json), [changelog](https://github.com/jackwener/OpenCLI/blob/main/CHANGELOG.md), recent issues, and open/closed PRs.

The source built the Rest.li query by concatenating user values with structural delimiters, then URL-encoded the whole query and restored `%2C`, `%3A`, `%28`, `%29` globally. This incorrectly restored delimiter characters *inside values* as grammar tokens. Prior LinkedIn [PR #2567](https://github.com/jackwener/OpenCLI/pull/2567) concerned semantic-search migration and closed unmerged; [PR #2588](https://github.com/jackwener/OpenCLI/pull/2588) concerned localized UI labels and also closed unmerged. No duplicate PR fixing #2714 was found in targeted searches. The issue author offered to submit a fix but had not opened a matching PR in the inspected results.

Alternative OpenCLI issues: [#2711](https://github.com/jackwener/OpenCLI/issues/2711) needs Windows junction/concurrency/EPERM validation unavailable here; [#2698](https://github.com/jackwener/OpenCLI/issues/2698) requires pagination contract design; [#2697](https://github.com/jackwener/OpenCLI/issues/2697) needs a careful partial-coverage contract. #2714 had the clearest bounded, testable impact and publishable fork path.
