# Daily Autonomous GitHub Contributor — 2026-08-24

## Permanent workflow upgrade: missing fork is not a rejection reason
From now on, repository selection is based on contribution quality, not whether the account happened to fork the repository earlier.

### New execution sequence
1. Start from Repo-of-the-day and move forward through candidates.
2. Validate the issue/opportunity on current upstream `main`/default branch.
3. Search open/closed PRs and recent commits to avoid duplicate work.
4. If the opportunity is strong and no writable fork exists, treat fork creation as a required provisioning step.
5. Once a fork exists, sync its default branch to upstream before creating the contribution branch.
6. Create a narrowly named feature/fix branch.
7. Implement the smallest complete fix with regression coverage.
8. Run focused tests/lint/format and inspect the diff.
9. Push only the validated change to the fork.
10. Open a Draft PR against upstream with issue linkage and exact validation evidence.
11. Keep it Draft; never merge or mark ready automatically.

### Tooling reality checked today
The connected GitHub integration currently exposes repository reads, branch creation, commits, file writes, PR creation, CI inspection and related actions, but no direct repository-fork creation action. Therefore:

- the agent must never claim an automatic fork was created unless a real fork-creation action succeeds;
- absence of a fork must not downgrade the opportunity itself;
- when fork creation is impossible in the active toolset, record `blocked-by-fork-tooling` and continue to the next strong external Repo-of-the-day candidate;
- do not use our own repositories as a fallback merely because they are writable;
- when the GitHub integration gains fork creation, this step becomes automatic without changing the selection policy.

## Research sources and observations
- Today’s Repo-of-the-day scouting reached `bytedance/deer-flow`, then `backstage/backstage`, then `docling-project/docling`.
- DeerFlow was contribution-saturated across the high-signal small/medium issues checked, with many already having active or competing implementation PRs.
- Backstage and Docling were externally valid candidates but had no writable fork in the connected account.
- This exposed a workflow flaw: existing-fork availability was acting as a selection constraint when it should only be an execution dependency.

## Policy decision
A missing fork is no longer a valid reason to reject an otherwise strong external opportunity. The workflow will attempt to provision one whenever the available GitHub tooling supports it. Until then, it will continue searching externally and explicitly record the tooling block.

## Guardrails
- Never create duplicate PRs just because another repo is harder to provision.
- Never fall back to `GitHub-Contribution-Agent`, `Repo-of-the-day`, `quant-github-scout`, or another owned repo merely to produce activity.
- Never open a PR without dedupe checks and validation.
- Never merge or mark a PR ready automatically.
- Never claim fork creation, test success, or CI success without direct evidence.

## Action requiring user approval
None. This is now the default future workflow policy.
