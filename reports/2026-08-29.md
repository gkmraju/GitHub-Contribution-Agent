### Selected: DeerFlow #5065

Issue: **An MCP credential with a trailing newline gets echoed into a model-visible tool error**.

Issue link: https://github.com/bytedance/deer-flow/issues/5065

Duplicate PR search for `5065`, `trailing newline credential`, `header`, and `context_headers` found no competing pull request.

The current source at `backend/packages/harness/deerflow/mcp/context_headers.py` was inspected. For each configured request-scoped secret, the interceptor currently treats any non-empty value as valid and assigns it directly into the `resolved` header map before calling `apply_header_overrides()`. There is no validation for newline, carriage return, NUL/control characters, surrounding whitespace, or values that cannot be encoded by the HTTP transport.

This makes the issue independently reproducible at the code-contract level: malformed secret input reaches the downstream HTTP stack. The public issue documents that downstream `httpx`/h11 exceptions can include the rejected header bytes, while DeerFlow's tool error handling may surface exception strings to model-visible/persisted surfaces. The smallest correct boundary is therefore the request-scoped secret interceptor, before any secret value reaches the HTTP client.

## Why this matters

This is a credential-confidentiality and reliability fix. A user can accidentally supply a token read from a file or secret mount with a trailing newline. The tool call was already going to fail, but the failure should not contain the secret itself. Rejecting malformed values at the interceptor boundary keeps the failure actionable (by naming the configured secret key) while preventing the sensitive value from becoming part of an HTTP exception message.

The change does not weaken authentication or silently sanitize credentials. It fails closed and requires the caller to correct the secret value.

Message: `fix(mcp): reject unsafe request-scoped header values`

File changed: `backend/packages/harness/deerflow/mcp/context_headers.py`

Implementation details:

- Added `_is_safe_header_value(value)`.
- Rejects surrounding whitespace.
- Rejects ASCII control characters and DEL.
- Rejects values that cannot be encoded as Latin-1 for the transport path.
- Tracks invalid configured secret keys separately from missing keys.
- Invalid values raise a `ToolException` containing only the server name and configured secret key names.
- The invalid secret value is never interpolated into the warning or exception.
- Invalid credentials fail closed even when missing-secret behavior is configured differently.

## Risks and limitations

- The validator intentionally rejects all ASCII control characters, including horizontal tab, in request-scoped credential values. This is stricter than generic HTTP field-value grammar, but credential values should not require control characters and stricter rejection avoids secret-bearing downstream protocol errors.
- The change rejects surrounding whitespace rather than silently trimming it. This is intentional because silently changing authentication material can hide caller configuration errors.
- CI has not run yet; formatting/import/style issues may still be found by upstream checks after the Draft PR is opened.
- This change covers `headers_from_context`. The public issue also notes similar risk for `user_auth` credentials; that path was not expanded into this PR to keep the change independently reviewable and avoid unvalidated scope growth.
